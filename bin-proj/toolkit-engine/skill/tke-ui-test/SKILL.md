# UI 实机检查（tke）

**这是一种检查手段，不是在写测试资产。** 定位跟单元测试、API 测试一样：
改完代码，亲手在真机/真浏览器上走一遍，确认它真的能用，留下证据给人看。

你写完的功能，单测证明不了它在真实设备上能用——实现和测试都出自你，盲点重合。
这个 skill 给你的就是**一双手（操控）和一双眼（查看）**，外加**自动留证据**。

**tke 不带 AI、不需要 API key。** 怎么走、走到哪算完，你自己判断。

**三平台通用**：mac / Linux / Windows 上 tke 的命令完全一样。只有**外围的 shell 写法**
要按当前系统来——本文档的片段默认是 bash，Windows 上照 PowerShell 的等价写法改
（关键几处已给出两个版本）。路径同理：`~/.tke/logs/` 在 Windows 上是
`$env:USERPROFILE\.tke\logs\`。

## 什么时候该用（**不必等用户开口**）

你写完代码，单测和 API 测试证明不了**用户点下去真的有反应**——实现和测试都出自你，
盲点是重合的。所以这些时候**自觉跑一遍**，再把结论交出去：

- **改完前端 / UI 代码**：新页面、新组件、改了交互或样式
- **修完一个影响界面的 bug**：跑一遍复现路径，证明它真的不复现了
- **改了会体现在界面上的后端逻辑**：保存、下发、状态流转——去界面上确认它真的变了
- **交付之前**：要跟用户说"做好了 / 修好了"的时候，先有证据再说

不适用的：纯后端/纯算法改动、无界面的 CLI、文档。别为了跑而跑。

**做完给用户的是结论 + 一份报告链接**，不是一句"应该没问题"。

## 不要做的事

- **不要生成 `.tks` 脚本资产、不要建元素库（`.tklib`）、不要做回放验证。** 那是 `tke harness`
  的活（它的目标是产出未来可复用的测试）。你的目标只是**这一次检查**——用坐标操作就够了。
- **不要改产品代码来让检查通过。**
- **不要改账号状态、不要删数据。** 前置不满足就停下问用户。
- **凭据（密码/验证码/token）默认不要碰**——见下面「碰到登录怎么办」。

## 第 0 步：环境体检

```bash
tke doctor
```

> ### 报 `tke: command not found`？——**这台机器还没装 tke**
>
> 这个 skill 只是**文档**，`tke` 是个单独的二进制。一条命令装好（mac / Linux）：
>
> ```bash
> curl -fsSL https://cloud.test-toolkit.app/sl/preview/tookit-engine-resource/tke/install.sh | bash
> ```
>
> Windows（PowerShell）——**先落地再执行**，别用 `irm … | iex`：
> 那个脚本开头有 `param()` 块，管道执行会把它当成语句而报错。
>
> ```powershell
> $u="https://cloud.test-toolkit.app/sl/preview/tookit-engine-resource/tke/install.ps1"
> irm $u -OutFile "$env:TEMP\tke-install.ps1"; & "$env:TEMP\tke-install.ps1"
> ```
>
> **装完当前这个终端里还是找不到它**——安装器把 PATH 写进了 `~/.zshrc` / `~/.bashrc`，
> 只对新终端生效。你在同一个会话里继续跑，先让它立刻可用：
>
> ```bash
> export PATH="$HOME/.tke/bin:$PATH"     # Windows: $env:Path += ";$env:USERPROFILE\.tke\bin"
> ```
>
> 这句只让**当前会话**能用；让新终端也能用是安装器的事（它写 rc 文件）。
> `tke doctor` 里的「新终端」一项会告诉你这事有没有办成——它只查 rc 文件，
> **不看当前 PATH**（当前能跑不代表下个窗口能跑，P-33）。
>
> 然后再 `tke doctor`。**别去猜、别去翻源码构建**——装它就这一条命令。

三平台通用（Windows 也是这条），**不下载任何东西**。它会报：缺什么依赖、连了哪些安卓设备、
tke 版本、**这份 skill 是不是最新的**、日志落点、这台机能不能开浏览器窗口。

不通过就告诉用户缺什么，别硬跑。**缺依赖（chromedriver / Chrome / adb / go-ios）一条命令补齐**：

```bash
tke doctor                    # 只体检，不下载
tke doctor --fix --profile web    # 补网页那套（会问一句再下）
tke doctor --fix -y --profile web # 不问直接下
```

`tke doctor --fix`（旧名 `tke fix`，仍可用）是**唯一会联网下载的命令**——
别的命令缺东西只会报错指路，不会偷偷拖几百 MB。Chrome 有 600MB，下之前**跟用户说一声**。

> ### 报告 skill 过期时，先让用户更新再干活
>
> 体检里如果出现这样一行，**先停下来告诉用户**：
>
> ```
> skill    可用更新 · 20260817-040034
> ...
> ! 有可用更新　更新：tke update
> ```
>
> 你手上这份 SKILL.md 是旧的，**里面写的做法可能已经被修过了**——
> 拿旧文档去跑，很容易复现一个早就修好的问题，然后得出"这东西不好使"的错误结论。
> 更新就一条 `tke update`，十几秒。（`tke steps` 也会在过期时缀一行提醒，别忽略它。）

## 设备怎么给

每条 tke 命令都要 `-d` 指定操作对象——**tke 是无状态 CLI，不带 `-d` 会默认按 Android 处理**：

| 目标 | 参数 | 哪些机器能做 |
|---|---|---|
| 浏览器 | `-d web` | 都能 |
| 安卓 | `-d <序列号>`（`adb devices` 查） | 都能 |
| iOS | `-d <UDID>` | **只有 macOS** |

**iOS 只能在 macOS 上做**——设备上的 WebDriverAgent 必须先用 Xcode 装一次，而 Xcode 只有
mac 有。在 Windows/Linux 上碰 iOS 设备，tke 会直接拦下并说明，别把时间花在那儿。
（`tke doctor` 会告诉你这台机器能做什么。）

**安卓要启动 App 得知道包名 + Activity，不知道就查、别猜**：

```bash
tke -d <序列号> app focus     # 当前前台应用的包名和 Activity ← 最快
tke -d <序列号> app list      # 设备上所有第三方应用
```

**任务涉及多个设备时**（比如"在后台改配置，去手机上看有没有下发"），按语义分别指定；
**不确定用哪台就问用户**，别猜——打到错误的设备上可能有真实副作用。详见下面「跨设备检查」。

## 浏览器默认**无头**（不抢你的鼠标）

`-d web` 跑起来**不会弹窗口**。有头浏览器会抢走鼠标和焦点，人就没法一边跑检查一边干别的；
而无头与有头的渲染完全一致（同为 1280×813，元素坐标零差异），截图照样有。

要看着它跑，或者**需要人在窗口里手动操作**（登录、扫码、过验证码）时才开窗口：

```bash
tke -d web --headless=off steps '启动 ["https://..."]'   # 必须带等号
```

**开一次就够**：会话是跨命令复用的，后续命令不带参数会沿用那个有头窗口，
你手动登好的状态不会丢。想切回无头再显式 `--headless=on`（会重建会话，登录态清空）。

## 碰到登录怎么办

按这个顺序，**默认走第一条**：

**① 让用户自己在窗口里登（默认）** —— 凭据不进你的上下文、不进证据、不进任何日志：

```bash
tke -d web --headless=off steps '启动 ["https://后台地址"] # 开有头窗口，等用户登录'
# 然后停下来告诉用户："请在弹出的浏览器里登录，登好告诉我"
# 用户登完，后续命令照常跑（不用再带 --headless=off）
```

**② 用户主动把凭据给你，才代填**：他明说"账号 x 密码 y，你来填"时才做。
密码框里的值**在落盘前会被自动打码**（命令原文、页面结构、报告、截图横幅全都是 `••••••`），
所以证据可以照常分享——但凭据仍然在你的上下文和会话记录里，**别自己主动要**。

> **为什么默认是①**：`--log` 会把每步命令写进 log.json、渲染进报告、
> **还会烧进标注截图的顶部横幅**。打码是代码里的硬护栏（按真实页面认密码框，不靠你记得），
> 但"不知道的秘密最安全"——能不经手就别经手。
>
> 中途**别 `control close`**：那会把浏览器和会话一起清掉，用户刚登的状态就没了（C-6）。

## 主循环

### 1. 优先用**文字**操作，别绕坐标

```bash
tke -d web steps '点击 ["保存"]'          # ✅ 按可见文字点，执行时实时定位
tke -d web steps '点击 [{927, 112}]'      # ⚠️ 坐标：只在没有文字可依时才用
```

**这是最重要的一条。** 用文字的好处不只是省事：

- **不必先 `fetch`**——你知道要点"保存"就直接点，省掉一次全量元素表
- **一次可以传很多步**——文字在**每步执行的那一刻**才解析，页面变了照样命中；
  坐标则是一变就废，所以只能两三步一停、重新 fetch，token 就是这么烧光的
- **看得懂、可复用**——`点击 ["保存"]` 谁都读得懂，`点击 [{927,112}]` 明天就失效

`输入` / `选择` / `悬停` / `按压` 的第一个参数同样可以直接写文字。

**什么时候才需要 `fetch`**：不知道页面上有什么、文字点不中要看实际结构、或者要确认结果。

```bash
tke -d web fetch --interactive     # 可交互元素
tke -d web fetch                   # 全量（找纯文本内容用这个，见 pitfalls C-1）
```

输出里有 `text`、`bounds`、`resource_id`、`xpath`、以及 `<select>` 的 `options`。
**坐标是兜底**：图标没文字、多个同名元素要按位置区分时才用，
中心点 = `((x1+x2)/2, (y1+y2)/2)`。

图标没有文字、元素表里认不出来时：`tke -d web fetch --ocr offline` 用 OCR 补可读文字。

**这些情况必须读图，别用文本硬猜：**

- **下结论之前**——至少看最后一张标注截图。只凭元素表说"功能正常"，就是在拿"元素存在"
  冒充"用户看得见、能用"
- **文本表达不了的东西**：布局错乱/重叠、颜色与选中态、图表和图片有没有渲染出来、
  loading 卡住、弹窗遮挡
- **结果跟你预期不一样时**——先看图，别急着改坐标重试
- **操作后页面没如预期变化**——是点空了？被弹窗挡住了？看一眼就知道，猜十次也不一定对

**每步都读图确实会让 token 爆掉**（一张图约等于上千 token，二十步就是几万），
但**一次检查读两三张关键的图，成本可以忽略**。省 token 省到不敢看结果，是本末倒置。

`steps --log` 已经把**标注截图**存好了（顶部横幅=操作+成败、元素框、点击点、滑动轨迹），
路径在它输出的 `screenshot` 字段里——直接读那张，比 `refresh` 再截一张信息量大。

### 2. 操作——**用 `steps` 而不是 `control`，因为它会留证据**

```bash
tke -d web steps '点击 ["保存"]' --log ~/.tke/logs/<任务简称>/
```

`--log` 指的就是**这次检查的任务目录**，一个任务一份证据：

```
~/.tke/logs/<任务简称>/
├── report.html        ← 全程报告，**这就是给用户的交付物**
├── screenshots/       ← step_001.png, step_002.png …（跨批次连续编号）
├── pages/             ← 每步的**元素表 JSON**（等于"这一页的元素库"：有什么、能点什么、在哪）
├── raw_pages/         ← 每步的**原始页面**（浏览器 DOM / uiautomator / XCUI 原文，没被 tke 动过）
└── log.json           ← 每批的命令/成败/耗时
```

> ### 想回看页面？**读文件，别重新 fetch**
>
> 每步的页面结构已经存好了，`pages/step_003.json` 就是那一刻的元素表——
> 直接读它，比再跑一次 `fetch` 便宜得多，也不会把一大坨 JSON 灌进对话。
> （`fetch` 留给"我需要看**现在**这一刻"的时候。）
>
> **`pages/` 与 `raw_pages/` 的区别**：前者是 tke 筛过的（去掉了 svg/path 这类图标构件、
> 读屏专用的隐藏元素等），一屏通常几十个；后者是原始 DOM / uiautomator 输出，
> 上千个标签。实测同一页：**原始 1151 个标签 → 元素表 74 个**。
>
> 什么时候需要 `raw_pages/`：
> - **某个元素死活定位不到**，想确认它是被 tke 筛掉了、还是页面上压根没有
> - 要**对着原文写将来能复用的定位**（页面改版后，两份原文一比就知道改了什么）

**一次检查你会调很多次 `steps`——每次都用同一个 `--log` 目录**，
tke 会**接着上一批的编号往下写**，并把整份报告重建一次。

> ⚠️ **`--log` 目录名 = 任务身份。** 同一次检查里**一个字都不要改**（包括不要加时间戳、
> 不要按设备或步骤分）。换了名字就是另一个任务，证据会散成几份互不相干的报告，
> 而这件事**不会报错**——只有交付时才发现拼不起来。任务开始时定好那个名字，之后照抄。

**探索式也一样**：你想「走一步、看看、再决定下一步」完全可以——每次只传一两条指令，
只要 `--log` 不变，它们就是同一个任务，步骤照样连续编号、还是一份报告。
报告里不会因为你分了很多次调用而变乱（同设备的连续批次不留痕迹，
只有**换设备**或**中间停了很久**才会标一行，因为那两件事读报告的人需要知道）。

报告**自带截图**（内嵌），单个 html 发给人就能看全程，不用带着目录走。

### 每条指令后面用 `#` 写一句「这一步在干什么」

```bash
tke -d web steps \
  '启动 ["http://localhost:3000/settings"] # 打开设置页' \
  '点击 ["保存"] # 点保存，验证刚改的保存逻辑真的会落库' \
  --log ~/.tke/logs/save-fix/
```

**这句话会原样进报告**，显示在那一步的命令下面。**每条指令都写。**

为什么非写不可：报告里那行 `点击 [{927, 112}]` 谁也看不出你在干嘛。**你是当时唯一知道
「为什么点这里、期望发生什么」的人**——不写下来，这个信息就永远丢了，人复核时只能对着
坐标猜。写你的**意图和预期**（"点保存，验证会落库"），不要复述动作（"点击坐标 927,112"）。

`#` 只有在**引号外**才算注释，URL 里的锚点（`"https://x/#/list"`）和文本里的井号
（`"话题#标签"`）都不受影响。

**证据默认落 `~/.tke/logs/`，别往用户项目里写**——它是一次性检查的过程产物，
不该混进人家的仓库、也不该让人再去加一条 `.gitignore`。任务简称用能认出这次检查的词
（`login-fix`、`scene-sync`），方便过后翻。

> **什么时候该改到项目里**：证据要跟着 PR 走、要给同事在仓库里看，或者你的工具链只能
> 读项目内的文件——这时用 `--log .tke-ui-test/`，并**提醒用户把它加进 `.gitignore`**。

用 `control` 也能操作，但**什么都不会留下**，人就没法复核。

**一次 `steps` 可以传多条指令**，推荐按"一个决策轮"批量执行——证据目录也更好看：

```bash
tke -d web steps \
  '启动 ["http://localhost:3000/settings"] # 打开设置页' \
  '输入 ["标题", "冒烟-1430"] # 填标题，用能认出是本次测试的值' \
  '选择 ["模式", "日间模式"] # 选下拉项' \
  '点击 ["保存"] # 点保存' \
  --log ~/.tke/logs/<任务简称>/
```

**用文字定位就能这样一次传五步**——每步执行时实时解析，中途页面变了也不影响。
换成坐标就只能两三步一停、重新 fetch 算坐标，token 会翻好几倍。

### 别写 `等待`

**定位自带隐式等待**：元素没出现就自动重试，最多等 ~6 秒，**一出现就立刻继续**。
所以 `点击 ["保存"]` 后面**不需要**跟 `等待 [1s]`——那反而是死等，页面早好了也得站满一秒。
点击本身也会等到页面就绪（导航/客户端渲染都算）才返回。

只有这两种情况才真需要 `等待`：

- 等一个**没有对应元素**的过程：动画收尾、toast 自己消失
- 等**后端异步下发**——但那种场景用轮询更准（见跨设备一节），固定等待快了假失败、慢了白等

指令语法（`命令 [参数, 参数]`，无参命令写裸命令）：

| 用途 | 写法（优先用文字） |
|---|---|
| 打开 | web `启动 ["https://..."]` / 安卓 `启动 ["包名", ".Activity"]` / iOS `启动 ["BundleID"]` |
| 点击 / 长按 | `点击 ["保存"]` / `按压 ["卡片标题", 1000]` |
| 输入 | `输入 ["搜索框", "关键词"]` |
| **选择下拉** | `选择 ["模式", "日间模式"]` ← **web 的原生 `<select>` 只能用它**，点是点不开的 |
| 悬停（web） | `悬停 ["菜单"]` |
| **滚动到目标** | `滚动查找 ["文字", 上]` ← **目标在折叠下方时必须先用它**，见下 |
| 滑动 | `定向滑动 [{640, 450}, 上, 400]`（这个得给坐标） |
| 等待 | `等待 [2s]`——**默认不要写**，见下 |
| 返回 / 隐藏键盘 | `返回` / `隐藏键盘` |
| 切标签 / 切 App | `切换 ["2"]` / `切换 ["包名"]` |

第一个参数写 `"文字"` 就是按可见文字定位；写 `{x, y}` 才是坐标。**不需要建元素库**。

### 目标在视口外：先 `滚动查找`

**定位只看得见当前视口里的元素。** 目标在折叠下方时，`点击 ["文字"]` 不会自己去找它，
而是白等满 ~6 秒重试后失败——这一批后面的步骤也跟着中断。

```bash
tke -d web steps \
  '滚动查找 ["Memory safety", 上] # 向下滚去找目标（"上"=手指上滑=看更下面的内容）' \
  '点击 ["Memory safety"] # 滚到视口里了，直接点' \
  --log ~/.tke/logs/<任务简称>/
```

**纯文字、不需要元素库。** 它每滚一步都重新识别，滚到底/到顶自动停，你不用猜滚几次。
实测：同一个词，不滚直接点 = 失败 + 白等 9.1 秒；先 `滚动查找` = 0.4 秒找到、点中。

长页面（文档、列表、设置页）上，**只要目标不是首屏可见的，就先滚动查找**。

### 3. 确认结果

再 `fetch` 一次看页面变了没有，**并读那张标注截图**。判断"到底成没成"是你的事——
文本能证明"元素在"，证明不了"这一屏对不对"。

拿不准就把两样对上：你写的那句意图（`#` 注释）说的是什么，截图上真实发生的是什么。

## 跨设备检查（在 A 上做，去 B 上验）

典型："在管理平台创建一个场景，去手机 App 里看能不能正常查看和使用"。
tke 无状态、每条命令自带 `-d`，所以这本来就做得到——**难点全在别骗自己**。

**动手前先读 `reference/pitfalls.md`**（C-1 ~ C-6 全是这个场景的假结论陷阱）。顺序：

**① 先验起点**——去 B 上确认那东西现在**还不存在**（否则最后"看到了"可能是旧数据）。
用这次专用的名字（带时间戳后缀），跟历史数据撞不上。

```bash
tke -d <序列号> steps '启动 ["com.example.app", ".MainActivity"]' --log ~/.tke/logs/<任务简称>/
tke -d <序列号> fetch | grep -q "夜间回家-1430" && echo "⚠️ 起点就有同名的，换个名字"
```

```powershell
# Windows（PowerShell）
tke -d <序列号> steps '启动 ["com.example.app", ".MainActivity"]' --log $env:USERPROFILE\.tke\logs\<任务简称>\
if (tke -d <序列号> fetch | Select-String -SimpleMatch "夜间回家-1430") { "⚠️ 起点就有同名的，换个名字" }
```

**② 在 A 上做**。平台要登录就按上面「碰到登录怎么办」处理（默认切有头让用户自己登），
登完再继续——中途别 `control close`，会连登录态一起销毁（C-6）。

**③ 去 B 上等它出现**——固定 `等待 [30s]` 快了假失败、慢了白等。用 `--wait-text`：

```bash
tke -d <序列号> fetch --wait-text "夜间回家-1430" --timeout 30 \
  && echo "✅ 出现了" || echo "❌ 等了 30 秒仍未出现"
```

```powershell
# Windows（PowerShell）
tke -d <序列号> fetch --wait-text "夜间回家-1430" --timeout 30
if ($LASTEXITCODE -eq 0) { "✅ 出现了" } else { "❌ 等了 30 秒仍未出现" }
```

**出现即刻返回**（不是死等满），超时**非零退出**——所以 `||` / `$LASTEXITCODE` 天然接得住，
不会把"轮询跑完"误当成"东西出现了"。多个候选写 `"名字A|名字B"`，任一命中即算。

> **别自己写 shell 轮询**（`for i in $(seq …)`）——忘超时、忘判命中、误用 `--interactive`
> 这三个坑每个都会让你得出假结论（C-1/C-3）。`--wait-text` 查的是**全量**元素，
> 不可点击的文本标签也找得到。
>
> 等不到时先想一下：它是**没出现**，还是**在视口外**？后者用 `steps` 的 `滚动查找`（C-15）。

**④ 验"能用"不只是"能看到"**——点进详情、执行一次，再 `fetch` 确认状态真的变了（C-5）。

**跨设备也用同一个 `--log` 目录，别按设备分**：每批自带设备名，报告会标出来，
步骤按时间排成**一条线**——正好还原"平台侧做了什么 → 手机侧看到什么"的因果顺序。
分成两个目录反而把这条因果链切断了，还要额外汇总一次。

```bash
tke -d web    steps '点击 ["保存"]'  --log ~/.tke/logs/scene-sync/   # 平台侧
tke -d <序列号> steps '启动 ["com.x", ".Main"]' --log ~/.tke/logs/scene-sync/   # 手机侧
```

## 交付给用户

**最后一定要跑这一条**——写上结论并把报告打开给用户看：

```bash
# 总结先写成文件（带表格的多行 Markdown 塞进命令行要跟引号搏斗）
cat > /tmp/summary.md <<'EOF'
已查看全部 2 个 player，均在线（v0.2.29）。

## 性能参数对比

| 参数 | Sydney | Melbourne |
|---|---|---|
| CPU | 1.09 负载 · 16 核 | 1.01 负载 · 4 核 |
| 温度 | 41.0°C | —（无传感器数据）|

- WS 延迟两台都偏高（327ms / 247ms），是页面里唯一的警示色指标
- Melbourne 读不到温度传感器
EOF

tke report ~/.tke/logs/<任务简称>/ \
  --task "用户让我验的那件事（写他的原话）" \
  --verdict pass \
  --summary-file /tmp/summary.md \
  --open
```

> ### 把**你在对话里给用户看的那份总结，原样**写进去
>
> 报告是给人留着的、也是转发出去的东西——**不要压缩成一句话**。
> 你在对话框里写了表格、列表、对照、注意事项，那就原样进报告：
> **表格 / 列表 / 小标题 / `**加粗**` / `` `代码` `` 都会被渲染出来**。
>
> 短结论用 `--summary "…"` 就行；**长的、带表格的用 `--summary-file`** ——
> 多行 Markdown 塞进命令行要跟引号和换行搏斗，先写成文件再指过来省事得多。
>
> 任务与结论在报告里是**最上面的独立卡片**：人打开第一眼看的就是这两样。

`--open` 会用系统默认浏览器打开报告（mac/Linux/Windows 都行；无图形界面时自动跳过）。

### `--verdict` 只有三种，别用错

| 值 | 什么时候用 |
|---|---|
| `pass` | 要验的功能**确实可用** |
| `fail` | **被测对象有问题**：功能坏了、复现了 bug、用户说的问题属实 |
| `blocked` | **没验成**：前提不满足、环境不行、被挡住了——不是被测对象的错 |

> ⚠️ **某一步没点中 ≠ `fail`。** 定位没命中、换个方式点中了，那只是过程里的一次无效
> 尝试，任务照样是 `pass`。`fail` 是留给「**这东西真的坏了**」的——你要为这个词负责，
> 因为用户会照它去改代码。拿不准就 `blocked` 并说清卡在哪。
>
> 不给 `--verdict` 时报告只写"已完成"，**不替你下结论**。

然后给用户：

1. **一句话结论** + **报告的绝对路径**（他才点得开）
2. 报告**自带截图**，可以直接转发（贴工单/群里），对方不需要那个目录
3. 发现的问题：**是产品 bug 就回去改代码**（这才是重点）；是你操作姿势不对就重来一次

要逐像素复核：点报告里的截图能跳到原图，或看 `screenshots/` 下的原始 PNG；
想要原图版报告加 `--full-image`。

证据默认在 `~/.tke/logs/` 下，不进用户仓库。**只有**你把 `--log` 改到了项目里
（`.tke-ui-test/`），才需要提醒用户加 `.gitignore`。

## 收尾

```bash
tke -d web control close      # web 省略包名即销毁会话（浏览器+driver+会话文件一起清）
```

web 会话跨命令复用，不关的话下次检查会从上次的页面开始。移动端不需要（除非你启动过 App 想关掉）。

## 并发

同时检查多个功能时，每次传独立的 `--cache <dir>`，否则共享工作区会互相覆盖。
