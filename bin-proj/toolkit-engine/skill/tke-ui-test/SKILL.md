# UI 实机检查（tke）

**这是一种检查手段，不是在写测试资产。** 定位跟单元测试、API 测试一样：
改完代码，亲手在真机/真浏览器上走一遍，确认它真的能用，留下证据给人看。

你写完的功能，单测证明不了它在真实设备上能用——实现和测试都出自你，盲点重合。
这个 skill 给你的就是**一双手（操控）和一双眼（查看）**，外加**自动留证据**。

**tke 不带 AI、不需要 API key。** 怎么走、走到哪算完，你自己判断。

**三平台通用**：mac / Linux / Windows 上 tke 的命令完全一样。只有**外围的 shell 写法**
要按当前系统来——本文档的片段默认是 bash，Windows 上照 PowerShell 的等价写法改
（关键几处已给出两个版本）。路径同理：`~/.tke/logs/` 在 Windows 上是
`$env:USERPROFILE\.tke\logs\`。

## 不要做的事

- **不要生成 `.tks` 脚本资产、不要建元素库（`.tklib`）、不要做回放验证。** 那是 `tke harness`
  的活（它的目标是产出未来可复用的测试）。你的目标只是**这一次检查**——用坐标操作就够了。
- **不要改产品代码来让检查通过。**
- **不要自动登录**、不要改账号状态、不要删数据。前置不满足就停下问用户。

## 第 0 步：环境体检

```bash
tke fix --check
```

三平台通用（Windows 也是这条）。它会报：缺什么依赖、连了哪些安卓设备、版本、
证据落点、这台机会跑有头还是无头。

不通过就告诉用户缺什么，别硬跑。**缺依赖（chromedriver / Chrome / adb / go-ios）可以一条命令补齐**：

```bash
tke fix --check          # 只看缺什么，不下载
tke fix --profile web    # 补网页那套（会问一句再下）
tke fix -y --profile web # 不问直接下
```

`tke fix` 是**唯一会联网下载的命令**——别的命令缺东西只会报错指路，不会偷偷拖几百 MB。
Chrome 有 600MB，下之前**跟用户说一声**。

## 设备怎么给

每条 tke 命令都要 `-d` 指定操作对象——**tke 是无状态 CLI，不带 `-d` 会默认按 Android 处理**：

| 目标 | 参数 | 哪些机器能做 |
|---|---|---|
| 浏览器 | `-d web` | 都能 |
| 安卓 | `-d <序列号>`（`adb devices` 查） | 都能 |
| iOS | `-d <UDID>` | **只有 macOS** |

**iOS 只能在 macOS 上做**——设备上的 WebDriverAgent 必须先用 Xcode 装一次，而 Xcode 只有
mac 有。在 Windows/Linux 上碰 iOS 设备，tke 会直接拦下并说明，别把时间花在那儿。
（`tke fix --check` 会告诉你这台机器能做什么。）

**安卓要启动 App 得知道包名 + Activity，不知道就查、别猜**：

```bash
tke -d <序列号> app focus     # 当前前台应用的包名和 Activity ← 最快
tke -d <序列号> app list      # 设备上所有第三方应用
```

**任务涉及多个设备时**（比如"在后台改配置，去手机上看有没有下发"），按语义分别指定；
**不确定用哪台就问用户**，别猜——打到错误的设备上可能有真实副作用。详见下面「跨设备检查」。

## 主循环

### 1. 看页面——文本是主输入，图在该看的时候必须看

```bash
tke -d web fetch --interactive
```

输出可交互元素的 JSON：`text`、`bounds`（坐标）、`resource_id`、`xpath`。**这是你的主要输入。**
元素中心点 = `((x1+x2)/2, (y1+y2)/2)`，就是你要点的坐标。

图标没有文字、元素表里认不出来时：`tke -d web fetch --ocr offline` 用 OCR 补可读文字。

**这些情况必须读图，别用文本硬猜：**

- **下结论之前**——至少看最后一张标注截图。只凭元素表说"功能正常"，就是在拿"元素存在"
  冒充"用户看得见、能用"
- **文本表达不了的东西**：布局错乱/重叠、颜色与选中态、图表和图片有没有渲染出来、
  loading 卡住、弹窗遮挡
- **结果跟你预期不一样时**——先看图，别急着改坐标重试
- **操作后页面没如预期变化**——是点空了？被弹窗挡住了？看一眼就知道，猜十次也不一定对

**每步都读图确实会让 token 爆掉**（一张图约等于上千 token，二十步就是几万），
但**一次检查读两三张关键的图，成本可以忽略**。省 token 省到不敢看结果，是本末倒置。

`steps --log` 已经把**标注截图**存好了（顶部横幅=操作+成败、元素框、点击点、滑动轨迹），
路径在它输出的 `screenshot` 字段里——直接读那张，比 `refresh` 再截一张信息量大。

### 2. 操作——**用 `steps` 而不是 `control`，因为它会留证据**

```bash
tke -d web steps '点击 [{640, 380}]' --log ~/.tke/logs/<任务简称>/
```

`--log` 会把这批操作的**标注截图 + 页面结构 + 日志**落到
`~/.tke/logs/<任务简称>/steps_<时间戳>/`（时间戳子目录由 tke 自动建，你不用管）。

**一次检查你会调很多次 `steps`，每次一个批次目录。** tke 每批跑完会自动重建
`~/.tke/logs/<任务简称>/report.html`——**这份全流程报告才是给用户的交付物**，
所有批次按时间接成一条线；各批次目录里那份 `report.html` 只是单批的细节。
**每次都用同一个 `--log` 目录**，别一批换一个，否则汇总不到一起。

### 每条指令后面用 `#` 写一句「这一步在干什么」

```bash
tke -d web steps \
  '启动 ["http://localhost:3000/settings"] # 打开设置页' \
  '点击 [{927, 112}] # 点保存，验证刚改的保存逻辑真的会落库' \
  '等待 [1s] # 等接口回来' \
  --log ~/.tke/logs/save-fix/
```

**这句话会原样进报告**，显示在那一步的命令下面。**每条指令都写。**

为什么非写不可：报告里那行 `点击 [{927, 112}]` 谁也看不出你在干嘛。**你是当时唯一知道
「为什么点这里、期望发生什么」的人**——不写下来，这个信息就永远丢了，人复核时只能对着
坐标猜。写你的**意图和预期**（"点保存，验证会落库"），不要复述动作（"点击坐标 927,112"）。

`#` 只有在**引号外**才算注释，URL 里的锚点（`"https://x/#/list"`）和文本里的井号
（`"话题#标签"`）都不受影响。

**证据默认落 `~/.tke/logs/`，别往用户项目里写**——它是一次性检查的过程产物，
不该混进人家的仓库、也不该让人再去加一条 `.gitignore`。任务简称用能认出这次检查的词
（`login-fix`、`scene-sync`），方便过后翻。

> **什么时候该改到项目里**：证据要跟着 PR 走、要给同事在仓库里看，或者你的工具链只能
> 读项目内的文件——这时用 `--log .tke-ui-test/`，并**提醒用户把它加进 `.gitignore`**。

用 `control` 也能操作，但**什么都不会留下**，人就没法复核。

**一次 `steps` 可以传多条指令**，推荐按"一个决策轮"批量执行——证据目录也更好看：

```bash
tke -d web steps \
  '启动 ["http://localhost:3000/settings"] # 打开设置页' \
  '输入 [{603, 112}, "测试内容"] # 填标题，用能认出是本次测试的值' \
  '点击 [{927, 112}] # 点保存' \
  '等待 [1s] # 等保存接口返回' \
  --log ~/.tke/logs/<任务简称>/
```

指令语法（`命令 [参数, 参数]`，无参命令写裸命令）：

| 用途 | 写法 |
|---|---|
| 打开 | web `启动 ["https://..."]` / 安卓 `启动 ["包名", ".Activity"]` / iOS `启动 ["BundleID"]` |
| 点击 / 长按 | `点击 [{640, 380}]` / `按压 [{640, 380}, 1000]` |
| 输入 | `输入 [{640, 380}, "文本"]` |
| 滑动 | `定向滑动 [{640, 450}, 上, 400]` |
| 等待 | `等待 [2s]` / `等待 [500ms]` |
| 返回 / 隐藏键盘 | `返回` / `隐藏键盘` |
| 切标签 / 切 App | `切换 ["2"]` / `切换 ["包名"]` |

坐标直接写数字，**不用建元素库**。

### 3. 确认结果

再 `fetch` 一次看页面变了没有，**并读那张标注截图**。判断"到底成没成"是你的事——
文本能证明"元素在"，证明不了"这一屏对不对"。

拿不准就把两样对上：你写的那句意图（`#` 注释）说的是什么，截图上真实发生的是什么。

## 跨设备检查（在 A 上做，去 B 上验）

典型："在管理平台创建一个场景，去手机 App 里看能不能正常查看和使用"。
tke 无状态、每条命令自带 `-d`，所以这本来就做得到——**难点全在别骗自己**。

**动手前先读 `reference/pitfalls.md`**（C-1 ~ C-6 全是这个场景的假结论陷阱）。顺序：

**① 先验起点**——去 B 上确认那东西现在**还不存在**（否则最后"看到了"可能是旧数据）。
用这次专用的名字（带时间戳后缀），跟历史数据撞不上。

```bash
tke -d <序列号> steps '启动 ["com.example.app", ".MainActivity"]' --log ~/.tke/logs/<任务简称>/phone-before/
tke -d <序列号> fetch | grep -q "夜间回家-1430" && echo "⚠️ 起点就有同名的，换个名字"
```

```powershell
# Windows（PowerShell）
tke -d <序列号> steps '启动 ["com.example.app", ".MainActivity"]' --log $env:USERPROFILE\.tke\logs\<任务简称>\phone-before\
if (tke -d <序列号> fetch | Select-String -SimpleMatch "夜间回家-1430") { "⚠️ 起点就有同名的，换个名字" }
```

**② 在 A 上做**。平台要登录就**停下来让用户在那个浏览器窗口里自己登**（你不许代登），
登完再继续——中途别 `control close`，会连登录态一起销毁（C-6）。

**③ 去 B 上轮询**——固定 `等待 [30s]` 快了假失败、慢了白等。先下拉刷新再轮询（C-4）：

```bash
found=0
for i in $(seq 1 15); do
  tke -d <序列号> fetch | grep -q "夜间回家-1430" && { found=1; break; }
  sleep 2
done
[ "$found" = 1 ] && echo "✅ 出现了" || echo "❌ 等了 30 秒仍未出现"
```

```powershell
# Windows（PowerShell）——同样要有超时，退出循环后同样必须判命中
$found = $false
foreach ($i in 1..15) {
  if (tke -d <序列号> fetch | Select-String -SimpleMatch "夜间回家-1430") { $found = $true; break }
  Start-Sleep -Seconds 2
}
if ($found) { "✅ 出现了" } else { "❌ 等了 30 秒仍未出现" }
```

> **用全量 `fetch`，别加 `--interactive`**——要找的名字往往是不可点击的文本标签，
> 加了会漏掉、等到超时报假失败（C-1）。循环后必须判命中，别把"跑完"当"通过"（C-3）。

**④ 验"能用"不只是"能看到"**——点进详情、执行一次，再 `fetch` 确认状态真的变了（C-5）。

**证据按设备分目录**：`--log ~/.tke/logs/<任务简称>/web/` 与 `.../phone/`。

跨设备时**收尾要手动汇总一次**（自动重建只管到各自子目录那层）：

```bash
tke report ~/.tke/logs/<任务简称>/
```

它会把两台设备的批次**按时间交错排成一条线**——正好还原"平台侧做了什么 → 手机侧看到
什么"的因果顺序，这份就是交付物。

## 交付给用户

1. **一句话结论**：功能能用 / 哪一步挂了 / 是什么原因
2. **全流程报告 `~/.tke/logs/<任务简称>/report.html`**（给**绝对路径**，用户才点得开）——
   双击看完整个检查：结论、每步命令、你写的那句「在干什么」、点中的元素、标注截图。
   **这是给用户的主要交付物**，不要甩一堆 `steps_*/` 碎报告给人
   - 要发给别人（贴工单/群里）：`tke report <目录> --embed` 出一份**内嵌截图的单文件**
   - 跨设备记得先 `tke report ~/.tke/logs/<任务简称>/` 汇总
3. 发现的问题：**是产品 bug 就回去改代码**（这才是重点）；是你操作姿势不对就重来一次

证据默认在 `~/.tke/logs/` 下，不进用户仓库。**只有**你把 `--log` 改到了项目里
（`.tke-ui-test/`），才需要提醒用户加 `.gitignore`。

## 收尾

```bash
tke -d web control close      # web 省略包名即销毁会话（浏览器+driver+会话文件一起清）
```

web 会话跨命令复用，不关的话下次检查会从上次的页面开始。移动端不需要（除非你启动过 App 想关掉）。

## 并发

同时检查多个功能时，每次传独立的 `--cache <dir>`，否则共享工作区会互相覆盖。

## 需要更多时（同目录，按需读）

- **`reference/pitfalls.md`** — **踩坑册**：会让你得出**假结论**的坑（不是跑不起来，是
  跑起来了、结论是错的）。跨设备检查前、下结论前、结果不对劲时读。**新踩的坑往里加**
- **`reference/tke-commands.md`** — tke 完整命令速查：元素采集/OCR、安卓应用与文件系统、
  设备信息、原生工具直通、排查日志在哪
- **`reference/steps-syntax.md`** — `steps` 指令的完整语法：全部指令、参数写法、
  滑动/滚动/长按/悬停/按键

上面主流程覆盖绝大多数检查；碰到"这个操作怎么写""包名从哪来""日志在哪看"时再翻。
