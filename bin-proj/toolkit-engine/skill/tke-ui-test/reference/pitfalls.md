# 检查踩坑册

**这里收的全是「会让你得出假结论」的坑**——不是"跑不起来"，而是**跑起来了、结论是错的**。
跑不起来你自己会发现；假结论不会自己冒出来，只能靠这份清单挡。

主流程在 `../SKILL.md`。这份按需读：写轮询前、下结论前、或者结果不对劲时。

> 只追加，不重写。新踩的坑往后加编号，写清**现象 → 原因 → 正确做法**。

---

## C-1 用 `--interactive` 找内容 → 假失败

**现象**：轮询等一个刚创建的东西出现，等到超时，报"没下发"。手工去看，明明在那儿。

**原因**：`fetch --interactive` **只输出可点击元素**。而你要找的名字往往是一个
**不可点击的文本标签**（标题、列表项文字、卡片上的名称），它根本不在这份输出里。

**做法**：**找内容用全量 `fetch`，不加 `--interactive`。**
`--interactive` 是给"我要点哪儿"用的，不是给"它出现了没"用的。

```bash
tke -d <设备> fetch | grep -q "夜间回家"        # ✅
tke -d <设备> fetch --interactive | grep -q "夜间回家"   # ❌ 纯文本标签会被漏掉
```

```powershell
tke -d <设备> fetch | Select-String -SimpleMatch "夜间回家"        # ✅ Windows
```

## C-2 没验起点 → 把旧数据当成功

**现象**：在平台上建了个场景，去手机上一看"有了"，报成功。其实那是上次测试留下的同名数据，
这次的下发根本没成。

**原因**：只验了终态，没验起点。跟"改完代码才截图、不知道改之前长什么样"是同一类错误。

**做法**：**动手前先去 B 上确认那东西现在不存在**；并且用**这次专用的名字**
（带时间戳/随机后缀），跟历史数据撞不上，复核截图时也一眼认得出。

---

## C-3 轮询没超时 / 不判命中 → "循环跑完"被当成"通过"

**现象**：日志里看着轮询跑完了，报告写"已确认出现"。实际一次都没命中。

**原因**：`for ... do grep -q ... && break; done` 跑完自然结束，**退出循环不等于找到了**。

**做法**：**别自己写循环**，用 `fetch --wait-text`——它出现即刻返回、超时非零退出，
"没等到"根本没法被当成"等到了"：

```bash
tke -d <设备> fetch --wait-text "夜间回家-1430" --timeout 30 \
  && echo "✅ 出现了" || echo "❌ 等了 30 秒仍未出现"
```

```powershell
# Windows（PowerShell）
tke -d <设备> fetch --wait-text "夜间回家-1430" --timeout 30
if ($LASTEXITCODE -eq 0) { "✅ 出现了" } else { "❌ 等了 30 秒仍未出现" }
```

多个候选写 `"名字A|名字B"`，任一命中即算。它查的是**全量**元素，不可点击的文本标签也找得到
（这正是 C-1 那个坑：手写轮询时误加 `--interactive` 会漏掉纯文本，等到超时报假失败）。

## C-4 App 没刷新 → 把"没刷新"当成"没下发"

**现象**：平台上建好了，手机上死活刷不出来，报"下发失败"。手动杀掉 App 重进，就有了。

**原因**：很多 App **只在进入页面时拉一次数据**，页面停着不会自己更新。

**做法**：轮询前先主动刷新——下拉，或退出重进页面：

```bash
tke -d <序列号> steps '定向滑动 [{540, 800}, 下, 400]' --log ~/.tke/logs/<任务简称>/
```

## C-5 只验"能看到"，没验"能用"

**现象**：列表里出现了这一行，报"功能正常"。用户点进去发现详情页是空的 / 执行报错。

**原因**：用户说"能正常查看和使用"是**两件事**，列表出现只完成了第一件。

**做法**：点进详情、执行一次（开关/触发/保存），再 `fetch` 确认状态真的变了。

---

## C-6 中途 `control close` → 把用户刚登好的登录态销毁了

**现象**：让用户在浏览器窗口里登录，登完继续跑，跑着跑着又要求登录。

**原因**：`tke -d web control close` 会把**浏览器 + driver + 会话文件**一起清掉，
登录态自然没了。web 会话是跨命令复用的，它就是登录态的载体。

**做法**：**只在整个检查结束时**关会话。中途要回到某个页面用 `启动 ["url"]`，不要关会话重开。

---

## C-7 会话被复用 → `--headless` 等开关静默失效

**现象**：加了 `--headless=on` 还是弹出了浏览器窗口；或者对照两种模式，结果一模一样
（**这是假阳性**，两次跑的其实是同一个浏览器）。

**原因**：web 会话跨命令复用，**已存在的会话是用什么参数建的就是什么样**，新参数不会回溯生效。

**做法**：换模式前先销毁会话：`tke -d web control close`。
（tke 会检测到模式不符并拦下重建，但别依赖它——养成先关的习惯。）

> **注意这条只对显式 `--headless=on/off` 生效。** 不带参数时 tke **沿用现有会话**，
> 不会因为"默认无头"就把你用 `--headless=off` 开的有头窗口销毁掉——
> 否则「开窗口 → 用户手动登录 → 继续跑」这条路根本走不通（登录态会在下一条命令就没）。

## C-8 用 `control` 操作 → 什么证据都没留下

**现象**：检查做完了，结论也对，但用户要看证据时只有一堆命令行输出。

**原因**：`control` 只干活不留痕；留证据的是 `steps --log`。

**做法**：**操作一律走 `steps --log <目录>`**。`control` 只在"确实不需要留痕"时用
（比如收尾关会话）。

---

## C-9 每步都截图读图 → token 爆掉

**现象**：检查做到一半上下文就满了。

**原因**：把 `refresh` 出来的截图每步都读进上下文。

**做法**：**主要输入是 `fetch` 的文本 JSON**，只在需要判断视觉状态（布局错乱、颜色、
图标形态）时才读图。图标认不出来时先试 `fetch --ocr offline` 补文字，比读图便宜得多。

⚠️ **但别矫枉过正**——见 C-11，从不读图会得出假结论，那比多花点 token 严重得多。

---

## C-10 打到了错误的设备上

**现象**：本该在测试机上做的操作，打到了另一台设备上（真实副作用）。

**原因**：多设备在线时靠猜；或者复制粘贴命令时 `-d` 没跟着改。

**做法**：**不确定用哪台就问用户，别猜**。跨设备任务里，两台设备的命令分别写清楚，
但**证据仍用同一个 `--log` 目录**——每批自带设备名，报告会标出来并按时间排成一条线，
正好还原"平台侧做了什么 → 手机侧看到什么"。分目录反而把这条因果链切断了。

## C-11 从不读图 → 拿"元素存在"冒充"功能可用"

**现象**：元素表里有那一行，于是报"功能正常"。用户打开一看：内容区空白、图表没渲染、
弹窗糊在上面、整块布局塌了。

**原因**：C-9 的过度修正。文本能证明"这个节点在 DOM/控件树里"，**证明不了"用户看到的
这一屏是对的"**。渲染失败、被遮挡、颜色状态错、图片没加载——元素表里全都一样。

**做法**：**下结论前至少读一张标注截图**。以下情况必读：

- 下最终结论之前
- 结果跟预期不一样（先看图，别急着改坐标重试）
- 操作后页面没如预期变化（点空了？被弹窗挡了？看一眼就知道）
- 要判断布局/颜色/选中态/图表/图片是否正常

一张图约上千 token，**一次检查读两三张关键的，成本可以忽略**。省 token 省到不敢看结果，
是本末倒置。

`steps --log` 存的是**标注截图**（顶部横幅=操作+成败、元素框、点击点），路径在输出的
`screenshot` 字段里——读那张比重新 `refresh` 一张信息量大。

## C-12 用坐标操作 → token 烧光、还没法复用

**现象**：一个跨端任务把整个会话的 token 跑光了；报告里全是 `点击 [{927, 112}]`，
过两天再看谁也不知道点的是什么。

**原因**：坐标一变就失效，所以**每两三步就得重新 `fetch` 一次全量元素表**。
实测一次跨端检查：20 个批次、47 步，平均每批 2.35 步，其中 22 步是 `等待`——
点一下、等一下、再 fetch 看一眼，token 就是这么烧掉的。

**做法**：**首选按文字定位**。

```bash
tke -d web steps '点击 ["保存"]'        # ✅ 执行那一刻才解析，页面变了照样命中
tke -d web steps '点击 [{927, 112}]'    # ⚠️ 只在没有文字可依时用
```

因为文字是在**每步执行时**实时解析的，所以可以**一次传五六步**而不怕中途页面变化——
批次数掉下来，fetch 次数跟着掉，token 就省下来了。而且 `点击 ["保存"]` 谁都读得懂。

## C-13 原生 `<select>`：点不开，也别去点

**现象**：想选下拉项，点开了却选不中；`fetch` 里根本看不到有哪些选项，只好绕道
用 python/JS 去读页面。

**原因**：原生下拉展开后，选项是**浏览器自己绘制**的，DOM 里依然不可见
（`getBoundingClientRect` 是 0）——点击路线在这儿走不通。

**做法**：用 **`选择`** 指令，它直接走 DOM 设值并派发 input/change 事件：

```bash
tke -d web steps '选择 ["模式", "日间模式"]'
```

`fetch` 现在也会把 `<select>` 的**当前值**和**全部可选项**带出来（`options` 字段），
所以你能先看清有什么可选。选了不存在的项，报错会把可选项列给你。

## C-14 到处写 `等待` → 测试慢一倍，还不可靠

**现象**：一次检查 47 步里有 22 步是 `等待`（占 47%），跑完花了好几分钟。

**原因**：以为"点完要等页面反应"。但 tke 的定位**自带隐式等待**——找不到元素就自动重试、
最多等 ~6 秒，**一出现就立刻继续**；点击本身也会等到页面就绪才返回。
再写 `等待 [1s]` 就是**纯粹的死等**：页面 200ms 就绪也得站满一秒，而真需要 3 秒时它又不够。

**做法**：默认**别写** `等待`。只有这两种情况才要：

- 等一个**没有对应元素**的过程（动画收尾、toast 自行消失）
- 等后端异步下发 —— 那种用轮询更准（C-3），固定等待快了假失败、慢了白等

```bash
# ❌ 每步都垫一个死等
'点击 ["保存"]' '等待 [1s]' '点击 ["确认"]' '等待 [1s]'

# ✅ 交给隐式等待，快的时候真的快
'点击 ["保存"]' '点击 ["确认"]'
```

## C-15 目标在折叠下方 → 文字定位必失败（不是"元素不存在"）

**现象**：`点击 ["Memory safety"]` 报「未找到包含文本 'Memory safety' 的元素」，
可你明明知道页面上有这个链接——往下滚一屏就看得见。

**原因**：**采集只收当前视口内的元素**。视口外的东西根本不在元素表里，
定位的隐式等待再等 6 秒也等不出来（它等的是"还没渲染完"，不是"在别处"）。
代价是白等 ~9 秒，**而且这一批后面的步骤全被中断**。

**做法**：目标不是首屏可见的，就先 `滚动查找`——纯文字、不需要元素库：

```bash
# ❌ 直接点视口外的东西
'点击 ["Memory safety"]'                 # 失败，白等 9.1s

# ✅ 先滚到它
'滚动查找 ["Memory safety", 上]'          # 0.4s 找到
'点击 ["Memory safety"]'                 # 点中
```

方向按"手指怎么滑"理解：**看更下面的内容 = 上**。它每滚一步都重新识别、滚到底会自动停。

## C-16 点到了"人看不见的同名元素"

**现象**：`输入 ["Search Wikipedia", "关键词"]` 报「点击后焦点落在 <label> 上，不是输入框」，
或者点击"成功"了但页面毫无反应。

**原因**：无障碍标签（`sr-only` / `screen-reader-text`）**人看不见，却带着那行文字**，
典型是 1×1 像素。定位按文字找，可能先命中这个幽灵点，点下去当然什么也没发生。

**采集层已排除这类元素**（1×1、`opacity:0`、`clip` 裁掉的），
同时把 `<label for>` / `aria-labelledby` / `title` 的文字并进对应输入框——
所以**输入框现在可以直接按它的可见标签定位**：

```bash
'输入 ["Search Wikipedia", "关键词"]'    # 直接命中真正的输入框
```

**还撞到同名的话**：用更具体的文字，或退回坐标（`fetch --interactive` 拿 bounds 算中心点）。

## C-17 中途换了 `--log` 目录名 → 一次检查散成几份报告

**现象**：交付时才发现证据拼不起来：`~/.tke/logs/` 下多了 `login-check/`、
`login-check-2/`、`login-phone/`……每个里面几步，没有一份是完整的。

**原因**：**`--log` 目录名就是任务身份**。探索式检查要调很多次 `steps`，中途换了名字
（加时间戳、按设备分、想到一个更贴切的词就改了）就等于开了个新任务。
**这件事不会报任何错**——每次调用都成功，报告也都生成了，只是各是各的。

**做法**：**任务开始时定好一个名字，之后一字不改地照抄**。

```bash
# ✅ 同一个任务，走一步看一步也没关系
tke -d web    steps '启动 ["http://localhost:3000"] # 先看看首页' --log ~/.tke/logs/login-fix/
tke -d web    steps '点击 ["登录"] # 看到登录入口了'            --log ~/.tke/logs/login-fix/
tke -d <序列号> steps '启动 ["com.x", ".Main"] # 去手机上验收'   --log ~/.tke/logs/login-fix/

# ❌ 这些都会各自成为一个新任务
--log ~/.tke/logs/login-fix-2/        # 手滑改名
--log ~/.tke/logs/login-fix-1430/     # 自作主张加时间戳
--log ~/.tke/logs/login-fix/phone/    # 按设备分（跨设备也用同一个目录，见 C-10）
```

**已经散了怎么办**：把各目录的 `screenshots/`、`pages/` 按时间顺序合并、编号重排后放进
一个目录，再 `tke report <目录>` 重建——但那很麻烦，**一开始别改名**便宜得多。

## C-18 代填的密码会进证据（而证据是拿去分享的）

**现象**：帮用户填了登录密码，检查做完把报告发出去——密码在里面。

**原因**：`--log` 会把每步命令写进 `log.json`、渲染进 `report.html`，
**还会烧进标注截图的顶部横幅**（像素里，删都不好删）。实测过：
`输入 ["密码", "hunter2"]` 就那样明晃晃印在图上。

**现在有硬护栏**：写进**密码框**的值会在落盘前自动打成 `••••••`——
命令原文、页面结构（`pages/*.xml`）、报告、截图横幅全都打码，判据是执行时的真实页面
（焦点落在 `type=password` 上），不靠你记得标注。所以代填之后证据可以照常分享。

**但仍然：默认别经手凭据。** 打码保护的是**证据**，保护不了**你的上下文和会话记录**——
密码进了对话就在那儿了。默认做法是切有头让用户自己登（见 SKILL.md「碰到登录怎么办」），
只有用户主动说"密码是 x，你来填"时才代填。

```bash
# ✅ 默认：开窗口，停下来等用户自己登
tke -d web --headless=off steps '启动 ["https://后台"] # 等用户登录'

# ✅ 用户主动给了凭据才这样（值会自动打码进证据）
tke -d web steps '输入 ["密码", "用户给的"] # 用户授权代填'

# ❌ 主动问用户要密码
```
