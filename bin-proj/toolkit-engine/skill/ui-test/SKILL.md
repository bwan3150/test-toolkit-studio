# UI 验收（tke）

你写完的功能，单测证明不了它在真实浏览器里能用——实现和测试都出自你，盲点重合。
这个 skill 让你**亲自操作一个真实浏览器**走一遍，并把过程固化成可回放的脚本。

**你就是这里的 AI。** tke 不带 AI、不需要 API key，它只提供设备操作原语和证据产出。
探索怎么走、什么时候算完成，由你判断。

## 通用约定

> **`-d web` 不能省**：`.tks` 本身不记平台，不带 `-d` 时 tke 按 Android 推断,
> 会报「adb 缺失」。web 用例的每条 tke 命令都要带 `-d web`。

## 职责边界

- tke 只产**脚本和证据**，**不改代码**。改代码是你的事。
- 发现的是产品 bug → 回去改代码；是脚本过时 → 更新脚本。两者要分清再动手。

## 第 0 步：前置检查

```bash
bash <此skill目录>/scripts/check-env.sh
```

不通过就**停下来告诉用户缺什么**，别硬跑。常见缺失：tke 不在 PATH、chromedriver 没跟 tke 放在同一目录、Chrome for Testing 没装。

## 第 1 步：先找有没有现成脚本（**这一步别跳**）

```bash
ls tests/ui/*.tks 2>/dev/null
```

**有对应脚本 → 走 A（回放）。没有 → 走 B（探索）。**

A 是秒级、零成本、结果确定的；B 要几十轮设备操作。**不要因为 B 更"彻底"就默认走 B**。

---

## A. 回放验证（有脚本时）

```bash
tke -d web run tests/ui/<feature>.tks --log .tke-runs/
```

- 退出码 0 = 通过。**这是硬证据**（回放器真实执行了每一步和断言步）。
- 非 0 = 失败。看 `.tke-runs/<名>_<时间戳>/` 里的证据：
  - `log.json` — 哪一步失败、报什么错、耗时
  - `screenshots/step_NNN.png` — **每步标注截图**（顶部横幅=操作+成败、元素框、点击点、滑动轨迹）
  - `page/step_NNN.xml` — 当时的页面结构

**失败后先分诊，别急着改脚本**：

| 现象 | 判断 | 做什么 |
|---|---|---|
| 元素找不到，但页面上肉眼有等价元素（文案/位置变了） | 脚本过时 | 更新元素库（见 B 的落库步骤）或改脚本 |
| 元素在，点了没反应 / 报错 / 结果不对 | **产品 bug** | 回去改代码，别改脚本 |
| 页面根本没到 | 前置没满足（未登录、数据缺） | 停下问用户，**不要自动登录** |

> tke 的定位自愈（`--copilot`）需要 `[ai]` 配置，本 skill 场景下没有，所以失败会直接报错——
> 这是预期行为：失败交给你判断。

---

## B. 探索并生成脚本（没脚本时）

### 主循环（每轮）

**1. 看当前页面——用文本，不要每步截图**

```bash
tke -d web fetch --interactive
```

输出可交互元素的 JSON（含 text、坐标、xpath）。**这是你的主要输入**。

只在以下情况才看截图（`tke -d web refresh` 后读 `$TMPDIR/tke/workarea/web/current_screenshot.png`（路径以 refresh 的输出为准））：
元素表里分不清该点哪个、或需要确认视觉状态。**每步都读图会让 token 爆掉。**

**2. 决定并执行一个动作**

```bash
tke -d web control launch "https://example.com"   # 打开页面
tke -d web control click 640,380                  # 点击（截图像素坐标）
tke -d web control input "文本" --at 640,380       # 输入
tke -d web control swipe-dir 640,450 up 400       # 滚动
tke -d web control back
```

**3. 把这一步用到的元素落进元素包**

```bash
tke -d web element add "登录按钮" --lib tests/ui/<feature>.tklib --at 640,380 --desc "首页右上角登录入口" --cached
```

- `--lib` 指向**这个脚本自己的 .tklib**（没有共享元素库，两件套自包含）
- `--cached` 复用上一步 fetch/refresh 采集的页面，省一次采集
- 元素名要语义化（`登录按钮`），不要 `按钮1`
- 自动完成 crop 模板图 + ocr 文本

**4. 记下这一步对应的 .tks 行**（先记着，最后统一写文件）

### 循环终止

达成目标就停。**卡住的信号**：连续两轮页面无变化、或在同几个页面来回打转 → 停下来重新看整页元素，或问用户。

### 写 .tks 文件

```
# 用例: <一句话说清验证什么>
步骤:
启动 ["https://example.com"]
点击 [{登录按钮}]
输入 [{用户名输入框}, "testuser"]
等待 [2s]
断言 [{欢迎横幅}, 存在]
```

**语法**：`命令 [参数1, 参数2]`，无参命令写裸命令（`返回`、`隐藏键盘`）

| 参数 | 写法 |
|---|---|
| 元素 | `{元素名}`，指定策略用 `{元素名}&xpath`（可选 xpath/text/resourceId/contentDesc/className/ocr/img） |
| 坐标 | `{640, 380}` |
| 文本 | `"文本"` |
| 时长 | `2s` / `1500ms` |
| 方向 | `上` `下` `左` `右` |
| 存在性 | `存在` / `不存在` |

命令：`启动 关闭 点击 悬停 按压 滑动 定向滑动 输入 清理 隐藏键盘 返回 等待 断言 切换 滚动查找 断言页面 按键`

### 必须遵守的两条（**质量护栏，别省**）

1. **每到一个关键页面就插一条断言**（`断言 [{某元素}, 存在]`）。
   没有断言的脚本"跑通"毫无意义——它只证明没报错，没证明到了该到的地方。
2. **终点校验必须在收尾动作之前**。关浏览器/退出登录会销毁校验证据。

### 结束条件（**唯一标准**）

```bash
tke -d web run tests/ui/<feature>.tks --log .tke-runs/
```

**回放通过才算完成。** 不通过就回去修脚本（或确认是产品 bug），别把跑不通的脚本交出去。
你自己"觉得走通了"不算数——回放器真实执行才算。

---

## 交付给用户

1. `tests/ui/<feature>.tks` + `tests/ui/<feature>.tklib` — **两件套必须一起提交**，拷到别的机器就能跑
2. `.tke-runs/<名>_<时间戳>/` — 截图序列 + log.json（**审查证据**，通常不提交，加进 .gitignore）
3. 一句话结论：通过 / 失败在第几步 / 是产品 bug 还是脚本问题

建议把两件套 commit 进 repo——下次改这个功能，第 1 步就能直接回放，不用再探索一遍。

## 红线

- **不要自动登录**、不要改账号状态或删数据。前置不满足就停下问用户。
- **不要改产品代码来让测试通过**。
- 并发跑多个时，每次传独立 `--cache <dir>`（否则共享工作区互相覆盖）。
- 无头/有头由 tke 自动判断（无桌面自动无头）；要强制用 `--headless=on` / `--headless=off`（**必须带等号**）。
