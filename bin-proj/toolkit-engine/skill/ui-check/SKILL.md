# UI 实机检查（tke）

**这是一种检查手段，不是在写测试资产。** 定位跟单元测试、API 测试一样：
改完代码，亲手在真机/真浏览器上走一遍，确认它真的能用，留下证据给人看。

你写完的功能，单测证明不了它在真实设备上能用——实现和测试都出自你，盲点重合。
这个 skill 给你的就是**一双手（操控）和一双眼（查看）**，外加**自动留证据**。

**tke 不带 AI、不需要 API key。** 怎么走、走到哪算完，你自己判断。

## 不要做的事

- **不要生成 `.tks` 脚本资产、不要建元素库（`.tklib`）、不要做回放验证。** 那是 `tke harness`
  的活（它的目标是产出未来可复用的测试）。你的目标只是**这一次检查**——用坐标操作就够了。
- **不要改产品代码来让检查通过。**
- **不要自动登录**、不要改账号状态、不要删数据。前置不满足就停下问用户。

## 第 0 步：环境体检

```bash
bash .claude/skills/ui-check/scripts/check-env.sh        # 项目级安装
# 或 bash ~/.claude/skills/ui-check/scripts/check-env.sh  # 用户级安装
```

不通过就告诉用户缺什么，别硬跑。

## 设备怎么给

每条 tke 命令都要 `-d` 指定操作对象——**tke 是无状态 CLI，不带 `-d` 会默认按 Android 处理**：

| 目标 | 参数 |
|---|---|
| 浏览器 | `-d web` |
| 安卓 | `-d <序列号>`（`adb devices` 查） |
| iOS | `-d <UDID>` |

**安卓要启动 App 得知道包名 + Activity，不知道就查、别猜**：

```bash
tke -d <序列号> app focus     # 当前前台应用的包名和 Activity ← 最快
tke -d <序列号> app list      # 设备上所有第三方应用
```

**任务涉及多个设备时**（比如"在后台改配置，去手机上看有没有下发"），按语义分别指定；
**不确定用哪台就问用户**，别猜——打到错误的设备上可能有真实副作用。详见下面「跨设备检查」。

## 主循环

### 1. 看页面——用文本，别每步截图

```bash
tke -d web fetch --interactive
```

输出可交互元素的 JSON：`text`、`bounds`（坐标）、`resource_id`、`xpath`。**这是你的主要输入。**
元素中心点 = `((x1+x2)/2, (y1+y2)/2)`，就是你要点的坐标。

需要看视觉状态时才截图（`tke -d web refresh`，路径在它的输出里）。**每步都读图会让 token 爆掉。**
图标没有文字、元素表里认不出来时：`tke -d web fetch --ocr offline` 用 OCR 补可读文字。

### 2. 操作——**用 `steps` 而不是 `control`，因为它会留证据**

```bash
tke -d web steps '点击 [{640, 380}]' --log .tke-check/
```

`--log` 会把这批操作的**标注截图 + 页面结构 + 日志**落到 `.tke-check/steps_<时间戳>/`。
用 `control` 也能操作，但**什么都不会留下**，人就没法复核。

**一次 `steps` 可以传多条指令**，推荐按"一个决策轮"批量执行——证据目录也更好看：

```bash
tke -d web steps \
  '启动 ["http://localhost:3000/settings"]' \
  '输入 [{603, 112}, "测试内容"]' \
  '点击 [{927, 112}]' \
  '等待 [1s]' \
  --log .tke-check/
```

指令语法（`命令 [参数, 参数]`，无参命令写裸命令）：

| 用途 | 写法 |
|---|---|
| 打开 | web `启动 ["https://..."]` / 安卓 `启动 ["包名", ".Activity"]` / iOS `启动 ["BundleID"]` |
| 点击 / 长按 | `点击 [{640, 380}]` / `按压 [{640, 380}, 1000]` |
| 输入 | `输入 [{640, 380}, "文本"]` |
| 滑动 | `定向滑动 [{640, 450}, 上, 400]` |
| 等待 | `等待 [2s]` / `等待 [500ms]` |
| 返回 / 隐藏键盘 | `返回` / `隐藏键盘` |
| 切标签 / 切 App | `切换 ["2"]` / `切换 ["包名"]` |

坐标直接写数字，**不用建元素库**。

### 3. 确认结果

再 `fetch` 一次看页面变了没有，或读那张标注截图。判断"到底成没成"是你的事。

## 跨设备检查（在 A 上做，去 B 上验）

典型："在管理平台创建一个场景，去手机 App 里看能不能正常查看和使用"。
tke 无状态，每条命令自带 `-d`，所以这本来就做得到——难点全在**别骗自己**。

### 先验起点，再动手（最重要的一条）

**动手前先去 B 上确认那东西现在不存在**，否则最后"看到了"可能是上一次留下的旧数据，
你会报一个假的成功。这跟"改完才截图"是同一类错误。

```bash
tke -d <序列号> steps '启动 ["com.example.app", ".MainActivity"]' --log .tke-check/phone-before/
tke -d <序列号> fetch | grep -q "夜间回家" && echo "⚠️ 起点就有同名的，先换个名字或让用户清掉"
```

> ⚠️ **找内容用 `fetch`（全量），不要加 `--interactive`。** 要验收的那个名字往往只是一个
> **不可点击的文本标签**（标题、列表项文字），`--interactive` 只输出可点击元素、会把它漏掉，
> 于是你等到超时、报一个假失败。`--interactive` 是给"我要点哪儿"用的，不是给"它出现了没"用的。

用**这次专用的名字**（带时间戳/随机后缀），跟历史数据撞不上，也方便复核截图时一眼认出。

### 平台侧要登录：停下来让用户自己登

管理平台通常要登录，而**你不许代登**（见「不要做的事」）。tke 的 web 会话是一个独立的
Chrome for Testing 实例，**跟用户日常浏览器不共享登录态**，所以也没有"已经登好了"这回事。

有头环境（mac/带桌面的机器）下这么处理：

```bash
tke -d web steps '启动 ["https://platform.example.com"]' --log .tke-check/web/
tke -d web fetch | grep -qi "登录\|login" && echo "需要登录"
```

看到登录页就**停下来告诉用户**："已经打开了浏览器窗口，请你在里面登录，登好回我一声。"
web 会话跨命令复用，用户登完你接着往下跑就行。**中途不要 `control close`**——那会把会话
连同登录态一起销毁，用户得重登。

（无头环境下用户看不见窗口、登不了，这类检查只能在有头机器上做。）

### 证据按设备分目录

```bash
--log .tke-check/web/      # 平台侧
--log .tke-check/phone/    # 手机侧
```

都堆一个目录里时间戳能区分、但人复核时看不出哪步在哪台设备上——分开放，交付时按
"平台侧做了什么 → 手机侧看到什么"讲。

### 等下发：轮询，不要固定 `等待 [30s]`

跨设备之间有下发延迟，固定等待**快了假失败、慢了白等**。

```bash
# 最多等 30 秒，出现就立刻继续（用全量 fetch，理由见上）
found=0
for i in $(seq 1 15); do
  tke -d <序列号> fetch | grep -q "夜间回家" && { echo "✅ 第 ${i} 次轮询看到了"; found=1; break; }
  sleep 2
done
[ "$found" = 1 ] || echo "❌ 等了 30 秒仍未出现"
```

**循环必须有超时、退出后必须判断有没有命中**——不然"没找到"会被你当成"循环跑完了=通过"。

> `.tks` 有重试断言（`断言 [{元素}, 存在, 15s]`），但**它需要元素库**，而这个 skill 不建元素库。
> 所以在这里就用上面这个 shell 轮询。

**手机侧可能要主动刷新才拿得到新数据**——很多 App 只在进页面时拉一次。轮询前先下拉刷新
或退出重进，别把"App 没刷新"当成"功能没下发"：

```bash
tke -d <序列号> steps '定向滑动 [{540, 800}, 下, 400]' --log .tke-check/phone/   # 下拉刷新
```

### 验"能用"，不只是"能看到"

用户说"能正常查看和使用"时，**列表里出现只完成了一半**。点进详情、执行一次（开关/触发），
再 `fetch` 确认状态真的变了。只验到"列表有这一行"就下结论，是漏检。

## 交付给用户

1. **一句话结论**：功能能用 / 哪一步挂了 / 是什么原因
2. **证据目录** `.tke-check/steps_<时间戳>/`：
   - `screenshots/step_NNN.png` — 每步标注截图（顶部横幅=操作+成败、元素框、点击点、滑动轨迹）
   - `page/step_NNN.xml` — 每步页面结构
   - `log.json` — 每步命令 / 成败 / 报错 / 耗时
3. 发现的问题：**是产品 bug 就回去改代码**（这才是重点）；是你操作姿势不对就重来一次

把 `.tke-check/` 加进 `.gitignore`——它是本次检查的证据，不是资产。

## 收尾

```bash
tke -d web control close      # web 省略包名即销毁会话（浏览器+driver+会话文件一起清）
```

web 会话跨命令复用，不关的话下次检查会从上次的页面开始。移动端不需要（除非你启动过 App 想关掉）。

## 并发

同时检查多个功能时，每次传独立的 `--cache <dir>`，否则共享工作区会互相覆盖。
