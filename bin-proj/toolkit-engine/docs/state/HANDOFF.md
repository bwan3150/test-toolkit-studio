### Q-9（最该做的那条）：语义定位这条路**当时是断的**

自己当调用方 AI，在本机 web 上实跑了一个普通链路（搜索 → 进条目 → 点内链）。
一趟就撞出**四个环环相扣的洞**——单修任何一个这条路都还是断的：

| # | 洞 | 后果 |
|---|---|---|
| P-28 | `sr-only` **1×1 像素**幽灵元素带着那行文字进了元素表，还排在真元素前面 | `输入 ["Search Wikipedia", …]` 点在幽灵点上 |
| P-28 | 真输入框**一个字都没有**（可见名称来自 `<label for>`，采集只认 `aria-label`/`placeholder`） | 输入框根本没法按文字定位 |
| INV-9 | 点空后报「当前没有聚焦的输入框（**请先点击输入框**）」 | **把 AI 直接引回坐标路线** |
| P-30 | 文字定位只看得见**视口内**元素；破解它的 `滚动查找` 被文档标成"需要元素库" | 视口外目标必失败 + 白等 9.1s，而那个能力**一次都没被用过** |

**修完的对照**（同一步、同一页面）：

- `输入 ["Search Wikipedia", …]`：**失败** → 1315ms 通过 → 去掉 500ms 白等后 **886ms**
- `点击 ["Memory safety"]`：不滚 = 失败 + 白等 **9.1s**；先 `滚动查找` = **0.4s** 找到 + 点中
- 整批 3 步：**纯语义、零坐标、零 fetch**

**顺带量到的 token 事实**：一次 `fetch --interactive` = **32KB ≈ 8K token**，而 fetch 本身只要
237ms。**贵的从来不是时间，是每次重新 fetch 的那张表**——和上一场"坐标路线烧 token"的诊断对上了。

### Q-8：`fetch --wait-text` 落地（ADR-0013）

`tke -d <设备> fetch --wait-text "文字" --timeout 30`：出现即刻返回、超时**非零退出**。
skill 文档里所有手写 shell 轮询范例**全部替换**。
没等 mac 实测就定，因为 Q-9 给了独立佐证：**靠文档传递能力是脆的，靠退出码传递结论是硬的**。

### Q-4：关闭。wda/web **没有** adb 同款无限挂

17 处 ureq 调用 **1:1 都带 timeout**，等待循环全是有界 `(0..N)`。
根本差异：adb 是 spawn 子进程（没有任何自带超时，所以 P-03 必须兜底），web/wda 走 HTTP 由 ureq 兜底。

### Q-10：移动端**没有** P-27 式白等，但查出反向同族

`adb`/`wda` 的 `tap` 后根本不等（只有 web 有 `wait_ready`），所以不存在"等满"。
反而是 **web 吃了移动端才需要的 500ms 软键盘等待**（P-29，已修，占该步 ~38%）——
与 P-27 同族：**一个语境下正确的等待被搬到了不需要它的语境**，不报错、只是悄悄变慢。

### 追加：证据组织重做（用户看完报告后的反馈）

用户的原话是**"这种 log 和 report 的组织方式很乱"**。之前每调一次 `steps` 就是一个
`steps_<时间戳>/`，调十次 = 十个目录 + 十一份报告。现在 `--log` 就是任务目录、
反复调用**续写**，`<任务>/{report.html, screenshots/, pages/, log.json}`，步骤跨批次连续编号。

- **只改 `steps`**（用户拍板）：run/flow/harness 每次是独立回放，保持时间戳目录才好对比
- **跨设备不再分目录**：每批自带 device，报告按时间排成一条线还原因果
- **报告默认自包含**（缩放 960 + JPEG82 内嵌）：5 步 1.7MB → 598KB，单文件直接转发
- 又一次"先量再改"：**光转 JPEG 几乎不省**（PNG 对纯色压得好、JPEG 在文字锐边吃亏），
  真正省的是缩放——第一版用 1280 宽量下来基本没降

## 埋的坑 / 后来人注意

- **这场最大的教训**：上一场把 SKILL.md 掉头到语义定位就以为成了，**但没人真的走一遍**。
  实跑一次的成本极低（十几分钟），却发现这条路当时**根本走不通**。
  **改完文档不等于能力可用——必须自己当一次调用方，从头走一遍真实链路**。
- **P-30 的真正形态是文档坑**：`滚动查找` 的能力一直都在、也不需要元素库，
  但文档写成"需要元素库"，于是 AI 一次都没用过。**与 90d9dcad 同型**
  （能力早就有，只是没告诉 AI／告诉错了）。**这个模式已经出现两次了，下次先查"是不是文档在骗人"**。
- **给 AI 的元素表必须与人眼所见一致**：多一个人看不见的元素，就多一个静默点空。
- 加新的固定 `sleep` 前先问：**哪个平台需要它？其他平台呢？**（P-29）
- 环境可复现：Chrome 在 `~/.local/share/tke/chrome-linux64/`，chromedriver 与 tke 同目录；
  本机 tke 在 `studio/bin/linux-amd64/`（`build-linux.sh --no-ocr --quiet` 产出）。
