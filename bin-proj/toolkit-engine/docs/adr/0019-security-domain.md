# ADR-0019: `tke security` —— 探索式黑盒安全测试，作为 tke 的第二个 agent 领域

- **状态**: 生效（P0 设计锁，用户 2026-08-25 拍板；INV-13/14/15 已写入 INVARIANTS.md）
- **日期**: 2026-08-25
- **关联**: INV-1（接地）/ INV-5（不泄题）/ INV-9（失败可见）/ ADR-0002（编排官无固定流程）/
  ADR-0009（五态出口）/ ADR-0011（设备成为工具参数）/ ADR-0016（删 CLI 直通·无无证据第二路）/
  参考基线 `konec-sanity-security.html`

## 背景

harness 是「能操作屏幕的 agent」——它的动作是点击/输入，感知是 UI 元素树。
安全测试是**另一个领域**：动作是 HTTP 请求 / 侦察 / 注入探测，感知是响应码/头/响应体/JS bundle/TLS，
不是屏幕。硬塞进现有 harness 会把两套完全不同的工具集和角色搅在一起。

用户拍板（2026-08-25）三条范围：
1. **泄露类 + 主动注入**（SQLi/XSS/SSRF 等）都做，不只被动侦察。
2. **信任操作者**——不立硬 scope 授权门，法律责任归操作者。
3. **三档信息全做**：无信息（纯黑盒）/ 有 API 文档 / 有完整代码（源码灰盒）。

同日补充（2026-08-25）：把「单一信任模式」改成**强度阶梯**——真黑客不会因为危险就不做，
要验「完全防御」就得允许危险动作；但有大量真实用户的生产项目又得能上轻档别打坏。
于是强度做成一条可选阶梯（默认最安全），再加一个正交的「只测某一面」过滤器。见决策第 5 条。

目标形态：产品（不同信息情况）→ 多方式自动探索的黑盒测试 → 全局安全水平报告 →
若有真实漏洞，则在全局报告外再各出一份独立漏洞报告。可交互（复用 harness 的 TUI），
`--json` 可接 Electron app 或无头服务器。

## 决策

新增第二个 agent 领域 `src/workflow/security/`。**骨架全复用，工具/角色/提示词另起一套。**

### 1. 复用 vs 新建

- 复用：`provider/LlmSession`（LLM 管道）、`ui/`（Plain / Json NDJSON / Tui 三前端）、
  `transcript/`、`report.rs` 的**自包含 HTML 技法**、`drivers/web`（浏览器侧侦察）、`ureq`（已带全链路 timeout，Q-4）。
- 新建：侦察/HTTP/注入工具集、角色（recon/prober/analyst/reporter）、
  `prompt/builtin/security/*.md`、两级报告模板、`evidence.rs`（统一证据落盘）。

### 2. 能力分层 = 照 device 那套（回答「要不要单独封装能力」）

**三层，同一份实现只写一次：**

- **primitive CLI 子命令**（确定性、可脚本、落证据、无 AI）——`tke http <method> <url> ...`（原始 HTTP 原语）、
  `tke recon <verb> <url>`（curated 被动检查：headers/cors/graphql/bundle/tls/endpoints/fingerprint）。
  等价于 `tke device control` / `tke app log`。
- **AI 工具** = 上面 primitive 的**薄封装**（`prompt/builtin/security/tools/*.md` + 同一份 Rust 实现），暴露给 agent。
- **`tke security`** = AI 编排层。

**给工具箱，不写死流程**（承 ADR-0002）：recon/prober 自行决定怎么组合，不是固定管线。
理由：① 有测试方向时可脚本、不烧 token；② primitive 能脱离 AI 单测（fake 后端）；
③ AI 与 CLI 同一份实现 = 「一个问题不该有两套答案」。
**每条路径都过 `evidence.rs`**——不留 ADR-0016 删掉的那种「无证据第二条路」。

命名开放项：`tke http` / `tke recon` vs 用户初提的 `tke api`——`api` 太窄（侦察还含 web 页/bundle/TLS），
建议 http+recon，用户可改。

### 3. 角色拓扑

```
recon  测绘攻击面 → prober 逐条假设去打 → analyst 对抗式复核 → reporter 出报告
```

`analyst` 是防假阳的闸门：每个 finding 要求**可复现证据**（复现命令 + 落成的 req/resp），
**软判断（AI 觉得像）与硬证据（真复现出来）分字段**（承 ADR-0009 第 4 条、asserter「踩实」）。
只有过闸门的 finding 才出单独漏洞报告。主动注入假阳率更高，这一步对它更严。

### 4. 三信息层级只改「种子来源」，后半段共用

| 信息 | 种子从哪来 |
|---|---|
| 无信息 | recon 现测：指纹 + robots/sitemap + 常见路径 + JS bundle |
| 有 API 文档 | `endpoints` 吃 OpenAPI/Swagger/Postman，声明端点直接进攻击面，逐个测鉴权/越权 |
| 有完整代码 | `source/` 读码找硬编码密钥/误配/注入 sink → 产出**假设**，交黑盒 prober 实打确认 |

**灰盒纪律：源码只提假设，漏洞判定必须黑盒复现**（见 INV-13）。

### 5. 强度阶梯 + 正交聚焦 + 出口

**强度阶梯 `--mode`（默认 `safe`）**——一条轴，从只看不碰到真黑客：

| 模式 | 做 | 不做 | 适用 |
|---|---|---|---|
| `passive` 被动 | 只侦察：指纹/头/robots/sitemap/公开 bundle/TLS | 不发任何主动探测/畸形请求 | 完全不想惊动目标 |
| `safe` 安全（默认） | 主动探测 + 注入**检测**（布尔/时延/反射）+ 越权**探测** | 不利用、不落库、不删改、不 DoS | 有大量真实用户的生产项目 |
| `aggressive` 激进 | 加**受控利用证明**：真拉一条数据证明可读、真越权取一条证明能取 | 仍不破坏/不持久污染/不 DoS | 预发/可控环境，要硬证据 |
| `red-team` 红队 | 真实攻击者视角：解锁破坏性/持久化/DoS **向量的可达性**验证 | 见下：不可逆动作设确认闸 | 上线前验完全防御、专门红队窗口 |

`red-team` 里**真正不可逆**的执行（真删数据、持续 DoS、写库持久化污染）默认走
「**证明向量可达 + 逐次显式确认才真扣扳机**」，而非无脑执行——理由正是「有大量真实用户的项目不该被误伤」，
要验完全防御，证明能到达破坏动作通常就够。全自动破坏档需用户另行显式放开（见 INV-15，重审触发点）。

**正交聚焦 `--focus auth|injection|data-exposure|transport|config`**：任意模式可叠加，只测某一面。

**其他默认与出口：**
- **授权按「信任操作者」**：启动仅一行操作者授权声明，不做硬 scope 门（用户拍板）。
- **五态出口**（承 ADR-0009）：`clean(0)` / `findings(非0，按最高危级编码)` /
  `needs_decision(2)` / `blocked(3，目标打不通)` / `error(4)`，写进报告 `outcome` 并映射退出码。
- **本次强度必落报告与 `findings.json`**（INV-15）：读的人一眼知道这次是用什么强度打的。
- `--json` NDJSON 事件流复用现成前端，结束给机器可读 `findings.json` + 报告路径。

### 6. 报告

两级产物：`security-report.html`（全局安全水平）+ `vuln-<slug>.html`（每个确认漏洞一份）。
自包含、离线可开、亮暗自适应、Toolkit 品牌留痕。细节见 `docs/security-report-spec.md`。

### 7. 新增不变量（已随本 ADR 生效，写入 INVARIANTS.md）

- **INV-13 漏洞判定必须黑盒复现**：灰盒/源码/AI 直觉只能产「假设」，一个 finding 进报告
  必须有真实 HTTP 交互的可复现证据。——INV-1 接地原则在安全域的延伸。
- **INV-14 每个探测落证据，无无证据的第二条路**：所有探测（CLI primitive / AI 工具）
  统一过 `evidence.rs`。——承 ADR-0016 精神。
- **INV-15 强度默认最安全，升档显式，破坏不可逆需逐次确认，模式必落报告**：主动探测/注入/利用/破坏
  按 `--mode` 阶梯解锁，默认 `safe`（只检测不利用不破坏）；`red-team` 才解锁破坏性/DoS 向量，且真正
  不可逆的执行（删数据/持续 DoS/持久化污染）需逐次显式确认。每次运行的强度写进报告与 `findings.json`。
  ——把「别打坏生产」做成结构而非口头约定。

## 理由与代价

**为什么分层而非只做 AI 工具。** 只做 AI 工具就丢了可脚本（有方向不烧 token）、可单测（fake 后端）、
单一真相源。device 已经用这条路验过——照抄比新造稳。

**为什么不立硬 scope 授权门。** 用户拍板信任操作者（2026-08-25）。代价：把法律边界交给操作者。
**重审触发**：一旦要对外发布 / 多租户 / SaaS 化，必须回补 scope 白名单 + 授权确认门。

**放弃了什么。** 默认档（`safe`）放弃主动利用与破坏，只到检测；利用/破坏要显式升档。
`red-team` 的全自动不可逆破坏（真删库/持续 DoS 自动扣扳机）暂不放开——留确认闸，
需用户另行显式要求才解锁（届时重审 INV-15）。

**何时重审整条 ADR。**
- 对外 SaaS 化（触发授权门回补）。
- 出现「灰盒/源码直接定漏洞、无黑盒复现」的 finding（违 INV-13）。
- 用户要求 `red-team` 全自动扣扳机、去掉不可逆动作的确认闸（改 INV-15）。
