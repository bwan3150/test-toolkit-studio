# ADR-0025 源码沙盒：让 harness 拿着图纸测，而不是盲盒探索

状态：已接受（用户 2026-08-28 拍板）
相关：ADR-0022（远程服务）、ADR-0023（平台对接）、ADR-0024（反向通道）、
INV-16（白名单）、INV-17（租约即隔离）、[提示词不得泄题]

## 问题

harness 今天能拿到的只有三样：页面元素表、截图、用户说的话。**被测对象对它是个盲盒。**

这一场在自己的模拟器上实测，代价看得很清楚：

- 任务是「打开设置，看 Android 版本」，模型绕了十几轮才找到路，每轮读一张截图 5.7 万 token。
  它不知道那一页在哪、也不知道怎么过去，只能一层层点着找。
- 定位只能靠**可见文字**。文案一改，脚本就废——而文案是最常改的东西。
- 元素表里连着几条「—」（安卓的「可点容器 + 里面的 TextView」结构），
  只能退回按坐标点，那是最脆的定位方式。

而这些信息**在源码里都是现成的、声明式的**：控件 id 是写死的，路由是列出来的，
这次改了哪些界面 diff 里就有。

用户提出：有些项目拿得到源码，能不能在节点机器上给每个项目开一个沙盒存 repo，
选他刚开发完准备测试的那个分支，据此让 harness 测得更准更快。

## 一条红线（先立，因为它决定后面所有接口形状）

> **源码只能用来回答「怎么找、去哪看」，绝不能用来回答「结果应该是什么」。**

不是洁癖，是这件事的成败所在。测试的价值在于**独立验证**：预期来自用例（需求），
观察来自真机。一旦让 AI 从源码里推断"点了之后应该弹这个框"，它写出来的就是

```
根据 SettingsActivity.kt:142，此处应显示成功提示 → 通过
```

——代码符合代码的同义反复。实现写错了它照样"通过"，而且**这种假结论看不出来**，
比没有这个能力更糟。这与已有的「提示词不得泄题」是同一条脉络：
AI 可见的东西一旦包含答案，它就不再去现场求证。

落到结构上（不靠提示词自觉）：

- 源码线索只从**定位/导航类工具**返回，这类工具的返回值只含「选择器、路径、文件名」
- **断言/判定路径拿不到源码**：asserter、监督官、finish 的判据都不接源码通道
- 报告里凡是引用了源码线索的步骤，标注它**只用于定位**

## 决定

**在节点机器上按 App 开源码沙盒，存 repo 工作副本。**

用户已知并接受下面三条代价（我提过另一条"平台提炼索引下发"的路子，
优点是源码和凭据都不下节点，代价是每种技术栈要写一套提炼器；用户选了工作副本）：

1. 公司源码会铺到每台测试机 → 用 §安全边界 缓解
2. 拉代码需要凭据 → 用**短期凭据**解决，见下（不违反 ADR-0023 的"业务凭据不下发"）
3. 版本同步要自己管 → 用 commit sha 对账，见下

**同时明确不做的**（这是范围的一半）：

- **不在节点上构建移动端**。安卓要 SDK/Gradle 缓存/签名，iOS 要 macOS + Xcode + provisioning
  —— 那是在重造一套 CI。待测包由**已有的 CI 产出**，tke 只负责拿来装上测。
- **不做部署编排**。Web 项目在节点上 `build && 起端口` 可以有（阶段三），
  但仅限单进程静态服务；需要数据库/依赖服务的，用预览环境 URL。

## 凭据：短期、按 repo、平台换发

节点**不持有** GitHub PAT / SSH key —— 那是长期业务凭据，与 ADR-0023 D6
（AI key 不下发节点）同一条理由：节点是"能被随时接上来的一台机器"，
不该成为公司资产的长期持有者。

改成：平台侧装 GitHub App，任务下发时用 installation token 换一个**一小时有效、
只对这一个 repo 只读**的凭据，随任务下发。节点用完即弃，不落盘。

```
平台 → 节点  {"source": {
                "repo": "https://github.com/acme/app.git",
                "ref": "feat/checkout-v2",
                "base": "main",                 // 算变更面用
                "token": "ghs_…",               // 1h，只读，仅此 repo
                "commit": "9f3c1ab…"            // 对账用，见下
              }}
```

拉不到就**明说拉不到**，然后照常跑（退回今天的盲盒模式）——源码是增益，不是前置条件。
把它做成硬依赖会让"源码服务挂了"变成"测试全线停摆"。

## 沙盒长什么样

```
~/.tke/sandbox/
└── <app_id>/                      # 按 App 隔离，不按 repo —— ACL 的粒度是 App
    ├── .git/                      # 裸镜像，只 fetch 不 checkout
    └── wt/
        ├── <session_id>/          # 每个会话一个 git worktree
        └── <session_id>/
```

**为什么是 worktree 而不是直接 checkout**：同一个 repo 会被多个会话同时用，
而每个人测的分支不一样（用户的原话就是"选择用户刚开发完准备测试的分支"）。
共用一份工作区意味着 A 的 checkout 会把 B 的代码换掉——而这**不会报错**，
表现是"线索莫名其妙对不上"，跟 P-63 一个味道。worktree 让每个会话有独立的工作树、
共用一份对象库（省磁盘、省带宽）。

生命周期与租约绑定（INV-17 的自然延伸）：

- 租约建立 → `git fetch` + 建 worktree（浅克隆，`--depth` 够算 diff 即可）
- 租约释放 → **删 worktree**，裸镜像留着（下次 fetch 是增量）
- 裸镜像按 LRU + 磁盘配额回收（默认给整个沙盒一个上限，超了从最久没用的 App 开始删）

## 节点侧的接口：三个工具，不是一个 grep

**不给 harness 一个通用的读文件/grep 工具。** 那等于把整个源码摊开在它面前，
上面那条红线就靠提示词自觉了——而提示词管不住这个。改成三个**窄接口**：

| 工具 | 回答 | 返回什么 |
|---|---|---|
| `changed_surfaces()` | 这次改动碰到了哪些界面 | 界面名 + 相关文件 + 改动规模 |
| `find_locator(说明)` | 这个控件的稳定定位是什么 | `resource-id` / `testID` / 无障碍标签 |
| `find_route(页面)` | 怎么走到那一页 | 入口 + 路径（Activity/路由/导航图） |

三个都**只回选择器和路径，不回代码行**。这是红线在接口层的兑现：
拿不到实现逻辑，就编不出"应该显示什么"。

它们与 `.tks` 的关系：`find_locator` 的产物直接进脚本，于是回放的抗改版能力
跟着上去了——这是顺带但可能更值钱的收益，因为今天的脚本靠可见文字定位，
文案一改就废。

## 版本对账：线索错了比没有更糟

源码线索指向的控件，必须真的在**当前被测的那个包**里。分支和包对不上时，
`find_locator` 会给出一个页面上根本不存在的 id，harness 会反复找一个不存在的东西——
比没有线索更慢。

所以：

- 任务下发带 `commit`，沙盒 checkout 到**那个 sha**（不是分支名——分支会动）
- 被测包若能读出构建元信息（安卓 `versionName`/`BuildConfig`、web 的 build id），
  与 sha 对账；对不上就**停用源码线索并说明**，不是硬着头皮用
- 报告里写清这次用的是哪个 sha —— 复盘时才说得清"线索为什么不准"

## 安全边界

沙盒把公司源码放到了测试机上，这是用户接受的代价，但要把边界写清楚：

- **按 App 隔离目录**，跨 App 不可见；节点上的会话只够得着自己租约对应的那个 App
- 源码**不进任何证据**：不进 `--log`、不进报告、不进截图横幅
  （P-45 的密码打码是同一条规矩：会被分享出去的东西里不能有它）
- **节点默认不开沙盒**，要显式 `--sandbox` 才启用 —— 一台随手接上来的机器
  不该因为接上了就自动开始存别人的源码
- 沙盒目录随节点卸载一并删除

## 分阶段

| 阶段 | 做什么 | 判据（可量化，达不到就停） |
|---|---|---|
| P1 | `changed_surfaces` —— 只做变更面聚焦 | 同一个用例的探索轮数 / token 降幅 |
| P2 | `find_locator` + `find_route` | 定位失败率降幅；生成的 `.tks` 里文字定位占比下降 |
| P3 | 接 CI 产物（apk/ipa/预览 URL）装上测 | 从"CI 出包"到"测完出报告"的人工步骤数 |

**P1 先做且只做一条，是因为它最便宜也最像**：提炼变更面不需要深度解析源码，
文件路径映射就已经有用；而它正对着用户的原始动机（"刚开发完准备测试的分支"）。
如果轮数和 token 降不下来，说明这条路不值钱——那就该及早知道，而不是把三个阶段
都做完才发现。

## 平台侧要配合的

- App 上多一处配置：repo URL + 默认分支 + GitHub App 安装关系
- 任务下发时带上 `source` 块（含短期 token 与 sha）
- 用例↔源码的反向关联（P2 之后）：改了 X 文件 → 哪些用例覆盖过 X → 只重跑那些。
  这条把源码接到**已有的用例库和运行记录**上，而不是另起一摊。

## 被否掉的方案

**把源码大段塞进提示词。** token 撑不住是次要的，主要是它直接踩红线：
AI 手里有实现，就不会去现场求证。

**平台提炼索引下发（源码不下节点）。** 安全和泄题风险都更低，同步只在一处管，
但每种技术栈要写一套提炼器，且断了"在节点上把项目跑起来"这条路。
用户选了工作副本，这条记在这里备查——**若将来提炼器成本被证明可控，
它仍是更安全的形态**，两者的工具接口（§三个工具）是同一套，可以平移。

**让 harness 自己 clone。** 凭据、配额、并发、清理全要它自己管，
而它是个 LLM 驱动的循环——这些必须是结构，不能是它记得做。
