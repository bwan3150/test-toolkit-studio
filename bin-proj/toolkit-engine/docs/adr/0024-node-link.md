# ADR-0024 内网节点：把任务通道反向成节点主动的长连接

状态：已接受（用户 2026-08-26 拍板）
相关：ADR-0022（远程服务）、ADR-0023（平台对接）

## 问题

ADR-0023 只把**心跳**做成了节点主动上报，任务通道仍然是平台 → 节点：
租会话、起任务、轮询状态、跑命令、列产物、取产物，七个调用全是平台发起 HTTP 打到
`node.base_url`。于是节点**必须让平台够得着**。

真机大多插在办公室或家里的机器上，那些机器在内网、IP 会变、没有公网入口。
现有的绕法都不满足用户的三个要求（内网 / 随时上下线 / 不拉 VPN）：

| 绕法 | 为什么不行 |
|---|---|
| 反向隧道（cloudflared / frp） | 能通，但每台机器要多配一个隧道、多一个要维护的公网入口；节点的接口只有一层 Bearer token，暴露面变大 |
| 平台与节点同内网 | 只适用于自部署；用户要的是"随时把一台机器接上来" |
| VPN / Tailscale | 用户明确不要 |

## 决定

**任务通道反向**：节点主动向平台建一条 WebSocket 长连接（`/api/v1/node/link`），
此后平台的所有调用都在这条连接上跑。节点只出不进。

- **连上即注册**，断开即离线 —— 不再需要 `--advertise`，也不需要平台够得着节点
- **注销 = 关掉连接**（或平台侧删掉节点行）
- NAT / 防火墙 / 动态 IP 全部不用管

## 怎么跑

**在连接上跑 HTTP 语义，而不是另发明一套协议。** 帧长这样：

```
平台 → 节点   {"id":"r7","method":"POST","path":"/v1/tasks","body":{...}}
节点 → 平台   {"id":"r7","status":202,"body":{...}}
节点 → 平台   {"event":"hello","devices":[...],"tke_version":"..."}   // 无需应答的上报
```

这么定有个直接好处：**两侧都不用重写业务逻辑**。

- 节点侧：收到帧就地拼成一个 `http::Request`，交给**已有的 axum Router**
  （Router 本身就是个 `tower::Service`），出来的 `Response` 再包成帧发回去。
  七个 handler 一个字都不用改，也不会出现"HTTP 走一套、WS 走另一套"的双份实现。
- 平台侧：`tkeclient` 抽出一层 `Transport`。原来的 HTTP 实现留着（同内网部署照样能用），
  新增一个走连接的实现：投一帧、按 id 等回执。调用方（排期器）一行不动。

**产物**同样走这条路（`/v1/sessions/{sid}/artifacts`）。二进制用 WS binary 帧分片，
不改"平台拉、节点不推"的原则（ADR-0023）——只是拉的方向变成在既有连接上问一句。

## 边界

- **一个节点一条连接**。同名重连时后来者顶掉前一条（机器重启、进程重启很常见，
  留着旧连接会让平台把任务投进一个已经死了的管子）。
- **在途请求随连接一起失败**，不做跨连接续传。任务本身有重排机制，
  比"猜猜这条请求到底执行了没有"要诚实。
- **平台是多副本时**，节点连在哪个副本上，任务就得在那个副本上派。
  当前是单副本，先不做跨副本路由；真要多副本时再加一层（Redis 里记 node→副本）。
  **不写进代码里的隐式假设都要在这儿写明**：现在这套只在单副本下正确。
- HTTP 那条路**不删**：平台与节点同内网时它更简单（少一条长连接要维护），
  而且它是这条新路出问题时的退路。节点两种模式由启动参数选，不自动切换 ——
  自动切换会让"到底走的哪条路"变成运行时才知道的事。
