# ADR-0011: 设备从「会话级全局」降为「工具级参数」——AI 按语义选设备

- **状态**: 提案（**待用户拍板**；flow per-script device 已先行落地，本 ADR 只管 harness/AI 侧）
- **日期**: 2026-08-12
- **关联**: ADR-0002（编排官 REPL）/ ADR-0010（skill 借调用方 AI）/ INV-7（两件套自包含）/ INV-12（不代办）
- **驱动场景**: 跨设备、跨平台测试——A 手机改设置 → B 手机看是否生效；web 后台下发 → 手机端验收

## 背景

`-d` 是**会话级全局参数**：`tke harness` 启动时（或向导里）定死一个设备，整场探索都在它上面。
但真实测试常常跨设备/跨平台，用户提的两个场景都是：

- 在 A 手机上调一个选项，去 B 手机查看是否同步
- 在 web 后台操作，去手机端看有没有下发成功

会话级设备表达不了这种流程。而且启动时就要人选设备，本身也别扭——**任务描述里其实
已经说清楚了要用什么设备**（"在手机上…再去后台…"），让人再选一次是多余的。

## 决策

**设备降为工具级参数：**

1. **`tke harness` 启动不再强制选设备**。`-d` 保留，语义变成「默认设备」（单设备场景照旧省事，
   向后兼容）；不给也能进对话。
2. **`explore` 等设备类工具带 `device` 参数**，由编排官按任务语义决定这一段跑在哪台上。
3. **一次 `explore` 仍只跑一个设备**——explorer 驱动循环内部不动。
   跨设备 = 编排官**多次调用 explore**（每次指定不同设备），产出多个两件套。
4. **新增 `list_devices` 工具**：AI 得先知道有哪些设备可用（Android 经 adb 列举、web 恒可用、
   iOS 需 UDID）才谈得上"按语义选"。
5. **不确定就问用户**（`ask_user` 已有）：设备选错会把操作打到错误的机器上，可能有副作用——
   **宁可问，不许猜**。
6. **跨设备测试的产物形态** = 多个两件套 + 一个 `flow.toml` 串起来，每项指定 device
   （flow per-script device 已落地）。编排官用 `save_file` 写 flow.toml 即可，不需要新工具。

## 理由与代价

**为什么一次 explore 只跑一个设备（而不是让驱动循环内部切设备）：**
这是本 ADR 最关键的取舍。让 explorer 在循环里切设备，要动感知/执行/元素库归属全链，
且一个 .tks 会变成多设备混合脚本——**回放层根本没有设备维度**（.tks 指令表里没有设备概念），
产出的东西回放不了，违背"探索产物必须可回归"。
拆成「一次 explore 一个设备 + flow 串起来」，explorer 内部零改动，产物天然可回放，
而且与 INV-7（两件套自包含）完全一致：每个 .tks 带自己的 .tklib，拷走即跑。

**代价：**
- **AI 选错设备的风险**。缓解：`list_devices` 给出真实清单 + 提示词要求不确定就问用户 +
  设备类工具把 device 作为**必填**参数（不给就没有默认可猜，逼它显式表态或问）。
  是否要对"有副作用的操作"再加一道确认，待实测后定。
- **跨设备的数据传递仍然缺**：A 上产生的动态值（订单号/验证码）传不到 B 的断言里，
  `.tks` 没有变量。用户举的两个场景不受影响（值是脚本里写死的已知值），但这是已知边界。
- **最终一致性/时序**：下发有延迟，B 上验收需要"轮询到出现或超时"，现在只有固定 `等待 [Ns]`，
  跨设备场景里特别脆。**建议与本 ADR 配套加「重试断言」**（单设备等异步结果同样需要）。
- 老行为兼容：给了 `-d` 且工具没指定 device 时，沿用 `-d`——不破坏现有单设备用法。

## 未决（实现前要定）

- 设备类工具的 `device` 是**必填**还是「缺省用 -d」？倾向必填（逼 AI 表态，避免默默打到错设备），
  但会让单设备场景的每次调用都啰嗦一点。
- iOS 设备如何进 `list_devices`（go-ios list 需要隧道就绪，代价比 adb devices 大）。
- 重试断言是否纳入本轮（它不属于设备语义，但跨设备验收几乎必用）。
